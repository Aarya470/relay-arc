# Relay Triage Engine

Our own emergency classifier. No API, no network, ~0.1 ms per call.
English, Hindi and Marathi.

```
lib/triage/index.ts            GENERATED — runtime + weights in one file
lib/voice-lang.ts              speech-recognition locales + language selector
ml/runtime_template.ts         the runtime source (edit this, not index.ts)
ml/corpus.py                   495 labeled utterances (en + hi + mr)
ml/featurize.py                feature spec + normalise map (mirrored in runtime)
ml/train.py                    trainer + exporter
ml/benchmark.py                head-to-head against Groq
tests/triage.test.ts           parity + behaviour suite
tests/parity.fixtures.ts       GENERATED by train.py — never hand-edit
```

Retrain and re-verify:

```bash
cd ml && python3 train.py
cd ../tests && node --experimental-strip-types triage.test.ts
cd ../ml && PER_CLASS=4 python3 benchmark.py     # needs GROQ_API_KEY for the cloud leg
```

## How it works

Multinomial logistic regression over binary n-gram features — deliberately simple,
because the whole point is that it runs on a phone with no signal and can explain
itself.

1. **Normalise** Indian-English and colloquial phrasing: `paining → pain`,
   `giddiness → dizzy`, `cant → cannot`, `unresponsive → not_responding`.
2. **Negation scope**: a negator suppresses the next 3 content tokens
   (`NOT_chest`, `NOT_pain`) — except terms that are themselves the symptom in
   negated form (`cannot breathe`, `not responding`, `cannot lift`), which are
   negation-immune.
3. **Features**: unigrams + bigrams over the non-stopword stream, preserving
   negation marks.
4. **Score**: softmax over 7 classes; the winning class's strongest positive
   features become human-readable *evidence*.
5. **Abstain** below 0.40 confidence and let the language model decide.

The engine ships as a single generated file with **no imports at all** — runtime
and weights inlined — so module resolution behaves identically in Next, webpack
and plain Node. Edit `ml/runtime_template.ts` and re-run the trainer; never edit
`lib/triage/index.ts` by hand. The lexicon lives inside the model, so the Python
trainer and the TypeScript runtime cannot drift. `tests/triage.test.ts` asserts parity against
fixtures produced by the trainer — if the two implementations ever diverge, that
test fails.

## Measured results

5-fold cross-validation over all 495 examples: **89.1%**.

Notably, that figure is unchanged from the 397-example English-only model even
though 98 Hindi and Marathi examples were added. Adding a second and third
language cost **zero accuracy** — see "Hindi and Marathi" below for why.

Head-to-head on 28 utterances the device model had never seen, against
`llama-3.1-8b-instant` using the exact prompt the product ships
(`docs/triage-benchmark.txt` is the raw run):

| | Relay Triage Engine | Groq llama-3.1-8b |
| --- | --- | --- |
| Accuracy (all cases) | 85.7% | **96.4%** |
| Accuracy when confident | **100%** (61% of cases) | — |
| Median latency | **0.11 ms** | 155 ms |
| Works offline | **yes** | no |
| Cost per call | **0** | metered |
| Explains its decision | **yes** | no |

**The honest read: Llama is more accurate than our model on raw classification,
and we are not going to out-classify an 8B model with 397 examples.** That is not
the win we are claiming.

The win is that **every single case our model got wrong, it abstained on**
(confidence 0.32–0.38, under the 0.40 gate). So in the shipped architecture:

- ~61% of emergencies are classified **on-device, instantly, offline, and — on
  this evaluation — with no errors**
- ~39% fall through to the language model, which is strong on exactly the
  ambiguous phrasings our small corpus is weak on
- If the network is unavailable, the on-device best guess is used rather than
  dead-ending an emergency

A model that knows when to be quiet is worth more here than a model that is
slightly more accurate but needs a network. Voice SOS now works with no signal.

## Hindi and Marathi

India is the launch market, and the voice SOS was recognising `en-US` only — a
Hindi speaker's emergency was being transcribed as nonsense before it ever
reached a classifier. Both are now first-class, in **Devanagari and romanised**
form (`सीने में दर्द` and `seene mein dard` both work).

The approach is deliberately not "train a second model". Hindi and Marathi terms
are **normalised onto the same canonical English tokens** the model already
learned, in `ml/featurize.py`:

```
सीने / seene / छातीत / chhati  →  chest
दर्द  / dard  / दुखत  / dukhat →  pain
सांस  / saans / श्वास  / shwas  →  breath
बेहोश / behosh                 →  unconscious
```

So `featurize('chest pain and sweating')` and `featurize('सीने में दर्द और पसीना')`
return the **identical** feature vector: `[chest, chest_pain, pain,
pain_sweating, sweating]`. Every English training example is simultaneously a
Hindi and a Marathi training example. That is why accuracy didn't move — the
model isn't learning three languages, it's learning one concept space that three
languages map into. It also means the whole thing still fits in 96 KB and still
classifies in 0.07 ms with no network.

`tests/triage.test.ts` sections G and H cover this: 10 Hindi/Marathi
classifications (both scripts), cross-lingual feature identity, and that Hindi
cardiac arrest — `बेहोश और सांस नहीं` — still routes to the CPR path.

The UI side is `lib/voice-lang.ts`: an EN / हिंदी / मराठी selector above the voice
button that sets the browser's `SpeechRecognition` locale, defaults from
`navigator.languages`, and remembers the choice. When the on-device engine
abstains, the spoken language is passed to the cloud fallback so romanised Hindi
isn't read as garbled English.

> **Caveat, stated plainly:** the Hindi and Marathi phrasings in `ml/corpus.py`
> were authored from general knowledge, not by native speakers. The mechanism is
> sound and tested; the specific vocabulary needs native-speaker review before we
> rely on it in production. It is marked as such in the corpus.

## Known weaknesses

- **Sparse-vocabulary phrasings.** Terms appearing once or twice are unreliable;
  every distinctive clinical term needs ≥3 phrasings in the corpus.
- **Stroke vs unconscious on speech symptoms.** "words coming out wrong",
  "cannot get my words out" lean unconscious. More stroke-speech data needed.
- **Injury vocabulary is thin** — "twisted my ankle badly" misfired. `other` is a
  grab-bag class and deserves subdivision.
- **Hindi/Marathi vocabulary is unreviewed.** See the caveat above. The coverage
  is also narrower than the English map — a phrasing outside the normalise map
  falls through to abstention (safe, but it means a cloud round-trip).
- **No Tamil, Bengali, Telugu or Gujarati yet.** The mechanism generalises; each
  additional language is a normalise-map expansion, not a new model.
- 495 examples is small. This model improves with data, and the real corpus
  should come from anonymised production transcripts under consent.

## Roadmap

1. Native-speaker review of the Hindi and Marathi normalise map and corpus.
2. Grow the corpus toward ~2,000 utterances, weighted to the weaknesses above.
3. Next languages by market size: Bengali, Telugu, Tamil, Gujarati.
4. Apply the same approach to **crash risk** and **health score**, which are
   currently LLM calls that would be better as explainable feature models —
   a medical flag should be able to state its reasons.
4. Make the recovery **timeline** deterministic clinical protocol rather than
   generated text.
